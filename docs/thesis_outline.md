# 卒業論文の骨子（案）

仮題：ブラウザ内で完結する英文構造可視化システムの開発
　　　―ルールベース解析による文型・品詞の提示と精度評価―

技術寄り（精度評価が中心）の構成。各章に「入れる表・図」と「出典ファイル」を対応付けた。
数値はすべて `results/summary_*.csv` と `results/<版>/REPORT.md` から取る。

---

## 第1章 序論
1.1 背景
- 英文読解における文構造（SVOC）把握の重要性と、学習者がつまずく点
- 既存の構文解析ツール（spaCy, Stanza 等）はサーバや大きなモデルが必要で、授業・自習の端末（スマホ、GIGA 端末）では使いにくい
- 生成 AI は便利だが、オフライン・無料・説明可能という条件を満たしにくい

1.2 目的
- サーバも AI モデルも使わず、ブラウザ内のルールベース処理だけで文型・品詞・訳語を可視化するシステムを開発する
- その精度を公開データと自作テストセットで定量評価し、ルールベースの到達点と限界を明らかにする

1.3 研究の問い（RQ）
- RQ1：ルールベース処理だけで、英文の品詞・文型をどの程度の精度で判定できるか
- RQ2：規則の規模（レベル1→3）と精度の関係はどうか。規則の追加は既存の精度を下げる（干渉する）か
- RQ3：誤りはどの文法現象に集中するか
- RQ4：長文（入試長文レベル）でも短文と同程度に動作するか
- RQ5：ルールベース（構造訳）と小型ニューラル翻訳は、サイズ・速度・出力の性質でどう異なるか（表 5-8：`results/v0.9/translation_summary.json`、比較例 `translation_comparison.csv`）

## 第2章 関連技術・先行研究
- 品詞タグ付け（POS tagging）と Universal Dependencies（UPOS 体系の説明）
- チャンキング（浅い構文解析）と 5 文型
- 軽量 NLP ライブラリ compromise.js の仕組み（辞書＋規則）
- 色覚多様性に配慮した可視化（色＋記号＋ラベルの併用）
- 開発用／評価用データの分離（機械学習の train/test 分割に相当）

## 第3章 システムの設計と実装
3.1 制約と方針（表 3-1：制約一覧 → 設計判断）
- GitHub Pages（静的サイト）、API キー不要、オフライン動作、AI モデル不使用
3.2 処理の流れ（図 3-1：`docs/architecture.md` の図）
- 文分割（text.js）→ 品詞タグ付け（pos.js）→ チャンク化（chunker.js）→ 変形・畳み込み → 文型判定（patterns.js）
3.3 品詞タグ付け：compromise のタグ → UPOS 風の粗い品詞、判定の優先順位（語彙 → 文脈 → be/do/have → ライブラリ）
3.4 チャンク化：名詞句・動詞句・前置詞句の規則、記号による区切り
3.5 文型判定：JSON 規則（表 3-2：規則一覧 `rules/patterns.json`、レベル別の件数）、特徴付き照合（linking / passive / naming / causative …）
3.6 レベル設計：規則に level を持たせ「level ≤ N だけ有効」にする。実験の軸として使う
3.7 長文対応：略語・引用・括弧・ダッシュ・同格・接触節・並列述語（表 3-3：記号と処理の対応）
3.8 可視化：色＋記号＋ラベル、ホバーカード（品詞・原形・役割・訳語）、構造図（SVG）、長文向け表示（図 3-2〜3-4：画面例）
3.9 辞書：EJDict-hand（パブリックドメイン）の加工方法
3.9' 構造訳：役割と辞書から日本語を組み立てる手順、限界（多義語の選択）
3.9'' AI 翻訳（任意）：ブラウザ内ニューラル翻訳 FuguMT の組み込み（Transformers.js / ONNX）、サイズ・オフライン・プライバシーの設計
3.10 オフライン化：Service Worker、PWA

## 第6章 考察
6.1 RQ1：到達点 — 品詞 約 88%（UD 規約）、文型 短文 約 94%、長文 約 73%。品詞誤りの主因（固有名詞／普通名詞、名詞／動詞の曖昧性）
6.2 RQ2：規則の規模と精度 — クロス表の対角線。レベル3規則を足しても L1・L2 の精度は下がらなかった一方、v0.5-pre で when 節の干渉が観測され、品詞の曖昧性解消で回復した事例
6.3 RQ3：誤り分析 — 評価用で残る誤りの文法項目（`results/v0.7/REPORT.md`）、根本原因はライブラリの品詞誤りと節の終端判定
6.4 RQ4：長文 — 文の長さそのものより、入試レベルの構文（接触節、挿入、並列）が原因。記号処理の効果（v0.5 → v0.6 で 30% → 100%（開発用））
6.5 開発用と評価用の差（99% vs 94%）が示すルールベースの汎化限界
6.6 教育利用の観点：説明可能性（適用した規則名を表示できる）、オフライン・無料、色覚配慮。学習効果の検証は今後の課題
6.7 限界：5 文型の枠に収まらない文、曖昧文（受動態と形容詞）、1 文 60 語超
